# PageID Selection Investigation: Summary

**Date:** 2026-03-22
**Duration:** Comprehensive investigation
**Status:** COMPLETE - NO ISSUES FOUND

---

## Question Asked

> "How is `pageid` chosen/selected in the bail system? Where could the wrong pageid be chosen (e.g., using a default, picking from a list incorrectly, joining on wrong fields)?"

---

## Answer

**PageID is never "selected" or "chosen" by the bail system.** It is:
1. **Extracted** from Facebook webhook events by replybot
2. **Stored** in the database with user state
3. **Returned** unchanged from SQL queries
4. **Sent** to botserver unchanged

**No selection logic, defaults, or fallbacks exist in the bail system.**

---

## Key Findings

### Finding 1: Pageid is Upstream Data
Pageid is generated by **replybot**, not the bail system:
- Replybot calls `getPageFromEvent(event)` on incoming webhook
- Extracts from `event.recipient.id` (or other fields for synthetic events)
- Stores with state when state is updated
- Bail system inherits pageid from database

### Finding 2: No Selection Logic in Bails
The bail system's approach:
- SQL: `SELECT DISTINCT s.userid, s.pageid FROM states s ...`
- Returns **all** pageids for matching users (no filtering)
- No WHERE clause conditions on pageid
- No JOIN logic that could select wrong pageid
- No configuration that overrides pageid

### Finding 3: Type Safety Throughout
- **Database:** NOT NULL constraint
- **Executor:** Type-checks pageid, skips if invalid
- **Sender:** Go struct enforces PageID field
- **Tests:** All test data includes pageid
- **Logging:** Invalid pageids logged as warnings

### Finding 4: Multi-Platform Support by Design
The composite key `(userid, pageid)` in states table means:
- One user can have multiple pageids (different platforms)
- Each combination is independent
- All combinations returned from query
- Each gets its own bailout event
- This is **correct behavior**

### Finding 5: Upstream Validation is Strong
Replybot's `getPageFromEvent()`:
- Priority: synthetic.page > echo.sender.id > recipient.id
- **Throws error if pageid cannot be determined** (no silent default)
- Prevents creation of state with missing pageid
- Bail system only receives states with valid pageids

## Potential Issues Investigated

### Q1: What if a state has a default pageid?
**Answer:** Impossible. Schema has NOT NULL constraint, no defaults defined.

### Q2: What if SQL query could return NULL pageid?
**Answer:** No. Query selects from states table which has NOT NULL, no LEFT JOINs that could introduce NULLs.

### Q3: What if multiple pageids exist for same userid?
**Answer:** Expected and correct. Composite key allows this. Each combination bailed independently.

### Q4: What if wrong pageid chosen when using OR conditions?
**Answer:** Not applicable. OR conditions filter on userid/state/form, not pageid. All matching pageids returned.

### Q5: What if CTE-based conditions lose pageid?
**Answer:** No. CTEs only add JOINs in WHERE clause. Main SELECT still gets pageid from states table.

### Q6: What if user_list has wrong pageid?
**Answer:** Prevented by validation. UserList.Validate() requires non-empty pageid.

### Q7: What if pageid is silently truncated?
**Answer:** No. Database field is VARCHAR unlimited, Go type is string unlimited.

### Q8: What if downstream (botserver) uses wrong pageid?
**Answer:** Out of scope for this investigation. Bail system sends correct pageid; botserver receives it.

## Key Takeaway

> **PageID is not "selected" by the bail system—it's inherited from the state stored by replybot, which derived it from the Facebook webhook event. The bail system respects this pageid completely, modifying it never, defaulting to it never, and selecting it never. This is the correct approach for a multi-platform system where user context (including which page they're on) matters.**
